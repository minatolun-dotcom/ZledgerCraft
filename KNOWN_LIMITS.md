# ZledgerCraft known limits and deferred work

Last updated: 2026-11-21

This is the persistent register of limits that are known but **not being fixed in
the current task**. It complements `ROADMAP.md`: the roadmap records what is
built and what is next, while this file records what is deliberately shallow,
deferred, or absent so it is not forgotten.

When a limit is removed, mark it resolved here and update the roadmap and
README. When a new limit is introduced, add it here in the same change.

## Platform, storage and operations

| ID | Limit | Current behaviour / consequence |
| --- | --- | --- |
| KL-01 | Browser storage is the default | Data lives in one browser profile's local storage. Clearing site data removes it. |
| KL-02 | Server workspace is optional; LAN authentication is basic | `data/workspace.sqlite` is shared by one server. LAN mode requires a server account and enforces owner/accountant/viewer roles plus company-level scoping. Recent revisions can merge independently changed records, including changes made by a scoped account. Voucher edit leases prevent two sessions from saving the same voucher concurrently; other overlapping changes still require a reload. The merge remains conservative and limited to retained history. |
| KL-03 | Cloud mode is opt-in and host-dependent | Node's built-in SQLite stores the LAN workspace; setting `DATABASE_URL` switches the workspace, revisions, leases, server audit, profiles, sessions, login/reset rate limits and account lockout state to Neon Postgres. Neon Auth handles credentials. The production API runs as a Neon Function behind a Cloudflare Worker; multiple instances share the tables and rate limits, and R2 provides the durable backup copy. Neon Functions can cold-start, local `/tmp` files are ephemeral, and the local SQLite fallback is per instance. There is no offline editing/merge. |
| KL-04 | Offsite backup is optional | Browser snapshots remain local to the browser. LAN mode keeps verified daily SQLite backups server-side. When R2 is configured, each verified snapshot is also uploaded offsite; the owner backup list merges R2 objects, downloads restore from R2 when the local copy is gone, and a failed upload keeps the local copy. Without R2 there is still no offsite copy. Downloaded JSON backups can be passphrase-encrypted in the browser; setting `ZL_BACKUP_PASSPHRASE` also encrypts new server/R2 backup files with AES-256-GCM. Without that key the server snapshots and R2 objects remain plaintext. There is no client-side encryption for automatic/R2 backups, remote-pruning policy in the app or network-share scheduler; use an R2 lifecycle rule for retention. |
| KL-05 | Workspace size and statement limits | Workspace saves are capped at 20 MB; a bank statement is capped at 5,000 lines. Day Book rendering is paged, but there is no server-side pagination, archival or retention strategy for very large workspaces and statements. |
| KL-06 | Single-file build has no server workspace | `dist/ZledgerCraft.html` works from `file://` but cannot use the optional workspace API. |
| KL-114 | Normalized rows are queryable, but nested settings stay JSON | Companies, account groups, financial years, cost categories, cost centres, units, stock groups, godowns, budgets, currencies, stock transfers, orders, BOMs, production runs, tax challans, ledgers, vouchers and voucher lines are relational tables. Company header fields, account-group name/parent/nature/key, financial-year dates/closed flag, cost-master name/category/creation time, unit name/symbol, stock-group and godown name/primary flag, budget name/target/year/amount/creation time, currency code/name/symbol/creation time, transfer date/godowns, order party/date/status/value, BOM output item and quantity, production run inputs and outputs, challan kind/date/amount/reference, stock-item identity/opening/batch fields and ledger opening, GSTIN, GST state, PAN, address, city, PIN, GST role and creation time are typed SQLite columns; the rest of each record remains JSON. Every top-level company collection now has a dedicated table, so masters, documents and registers are independently addressable. Nested configuration (GST/TDS/payroll settings, voucher tax/deduction detail and similar blocks) remains JSON inside its row, and there is no per-field query or merge for those nested values. Postgres still stores the whole workspace as one JSONB document. |
| KL-115 | Merge changes document numbers | Concurrent additions of the same voucher type and number keep the first number and reassign the later one. The reassignment is applied in the saved server workspace and the client is told how many numbers changed, but the original number is not preserved in a merge-conflict record. |
| KL-117 | Scheduled reports are a fixed daily summary | Delivery is once per UTC day at 02:30 when the Neon trigger runs; local mode checks hourly. The email/link contains a small management summary and one attached branded PDF, not a full report pack, statutory statement or workbook. The PDF uses built-in Helvetica, so non-Latin company/ledger names are transliterated to `?`, and large values may be truncated in narrow columns. A signed link is a bearer credential until it expires (default seven days), and recipients are configured server-side. The owner panel stores the latest 50 attempts (showing 10) but no per-message Resend webhook status or full delivery timeline. Failure alerts go to `ZL_ALERT_EMAIL` at most once per UTC day per running instance and cannot be delivered while Resend itself is unavailable. |
| KL-116 | Neon auth is shared; MFA remains unavailable | Postgres holds the workspace, revisions, leases, server audit, profiles, app sessions, login history, shared login/reset rate limits and account lockout state; Neon Auth verifies credentials. R2 provides a durable backup copy that can be listed and restored through the owner panel when an instance's `/tmp` copy is gone. Neon Auth mode cannot enforce the old TOTP/MFA, and R2 retention still depends on a bucket lifecycle rule. |

## Access, security and audit

| ID | Limit | Current behaviour / consequence |
| --- | --- | --- |
| KL-07 | Browser profiles are not authentication | In localhost/browser mode, owner/accountant/viewer are access-control profiles and anyone with the browser can switch them. LAN mode uses separate password-backed server accounts instead. |
| KL-08 | Resolved — company-level scoping added 2026-11-19 | Owners can assign a non-owner account to selected companies. The server filters reads, rejects hidden-company writes, and preserves hidden companies during scoped merges. Legacy accounts with no scope retain access to all companies. Localhost/browser profiles still see every company. |
| KL-09 | No live-workspace or vault encryption | Browser storage and the live SQLite/Postgres workspace are unencrypted. Downloaded JSON backups can be passphrase-encrypted in the browser with PBKDF2-SHA-256 and AES-256-GCM (secure contexts only), and new server/R2 backup files can be encrypted with `ZL_BACKUP_PASSPHRASE`. Server passwords are scrypt hashes, but books are not encrypted at rest. There is no TallyVault-style per-company vault. |
| KL-10 | Audit trail is app-level | The in-app log is append-only but not cryptographic or tamper-proof against direct browser/workspace/backup edits. LAN saves add a server-side hash-chained audit row and the owner view reports chain breaks, but a database administrator can still rewrite or re-hash the chain. |
| KL-11 | Limited account and session controls | SQLite/LAN accounts have TOTP two-step verification with one-time recovery codes, an owner-set per-account 2FA requirement, active-session listing/revocation, self-service password changes, persistent per-account/source lockout, sign-in history and an optional IPv4 allowlist. Neon Auth mode delegates passwords/reset to Neon Auth but has no TOTP/MFA; those routes and the 2FA requirement return 501. Voucher approvals are available per company, with an optional amount threshold so smaller staff vouchers can post directly; the submitter can revise or withdraw a pending voucher before a decision and each revision keeps field-level old/new values for the owner, there is no multi-level approval matrix, and concurrent pending-queue edits use the normal workspace conflict flow. |
| KL-12 | No external API or webhooks | The app has internal auth/workspace HTTP endpoints, but no public service API, webhooks or automation surface for integrations. |
| KL-113 | LAN transport is HTTP unless TLS is configured | Server passwords and workspace data are plaintext on the network by default. Set `TLS_CERT_PATH` and `TLS_KEY_PATH`, or use only a trusted private network; do not expose the port to the internet. The server still cannot obtain or trust a LAN certificate automatically. |

| ID | Limit | Current behaviour / consequence |
| --- | --- | --- |
| KL-13 | JSON backup is manual | Browser JSON backup/restore is manual; LAN mode adds scheduled SQLite snapshots and Neon mode adds Postgres JSON snapshots. There is no scheduled browser JSON export, branded PDF or Excel workbook backup. |
| KL-14 | CSV import is deliberately narrow | Imports ledgers, stock items, balanced multi-line vouchers and bank statements. |
| KL-15 | Missing from CSV import | Bill allocations, cheque/DD details, cost-centre allocations, currency masters, GST details, TDS/TCS details and arbitrary masters are not imported from CSV. Stock items, dated currency rates, units, stock groups, godowns, cost categories, cost centres, pay heads, currencies and employees with pay-head amounts are imported separately. The backup screen can also restore one named company from a backup and keep the other current companies, replacing a company with the same name or id. | KL-18 | Backup format is version 1 | No migration framework beyond tolerant normalisation. Older backups may lose unsupported fields. |
| KL-19 | Snapshot scope | Snapshots are browser-local, unencrypted and capped at ten, but any listed snapshot can be downloaded individually as JSON. There is no automatic pruning policy beyond the cap or client-side encryption of automatic snapshots. |

## Accounting and reporting

| ID | Limit | Current behaviour / consequence |
| --- | --- | --- |
| KL-20 | Resolved — multi-currency added 2026-11-18 | INR remains the base currency, with voucher-level foreign currency and a Forex Revaluation report. Remaining currency gaps are KL-64–KL-69. |
| KL-21 | Budgets support optional quarterly phasing | One budget per ledger/group per financial year, with an optional four-quarter split that must add up to the annual amount. Budget vs Actual exposes the phasing and budget-to-date for the elapsed quarter. There is no monthly phasing, revision workflow, approval, locking or carry-forward. |
| KL-22 | Cost centres are single-allocation per line | Each voucher line can carry one cost centre; there is no split across multiple centres or percentage allocation. |
| KL-23 | Unallocated cost is reconciled | Cost-centre rows still include only allocated lines, and the summary now shows unallocated debit, credit and net totals plus a ledger-wise unallocated table for the same period. There is no automatic allocation or per-voucher reconciliation between the two views. |
| KL-24 | No opening-adjusted cost-centre closing or payroll/stock budget | Cost reports include a category P&L and a ledger-wise movement break-up for each centre, both limited to tagged lines. Cost-centre opening balances are not modelled, so there is no opening-adjusted trial balance/closing; untagged income/expense allocation and payroll/stock budget by centre are also absent. |
| KL-59 | Resolved — cost categories and centres can be merged 2026-11-20 | A category or centre can be merged into another master; centres, category budgets, centre budgets and voucher-line allocations are reassigned before the source is removed. A merge is refused when both sides already have a budget for the same year. There is no bulk merge or bulk reallocation across several sources. |
| KL-60 | Overlapping budgets are summarised, not reconciled | A group budget and a ledger budget inside it can both exist. The report still lists both rows but totals exclude the nested budget and label it "Inside a group budget", so totals are not double-counted; there is no per-target reconciliation of the overlap. |
| KL-61 | Resolved — optional opening balances added 2026-11-20 | Budget actual defaults to net voucher movement from the financial-year start to the as-on date. An include-openings view adds each ledger/group balance brought forward at the year start (including prior-year activity), so balance-sheet or carry-forward budgets can use an as-on balance. Cost-centre and category budgets remain movement-only because cost-centre openings are not modelled (KL-31). |
| KL-62 | Budget changes keep an amount history | Editing a budget amount or name appends the previous amount, name and timestamp, and Masters shows the last 25 earlier amounts. Duplicating into the next year still copies only the current amount. There is no phased revision workflow, approval, bulk copy for every budget or full field-level audit trail. |
| KL-63 | Cost-category budgets cover all their centres | Budgets can target one cost centre or a whole cost category, measuring spend tagged to those centres. A centre budget inside a category budget is shown without double-counting, and budgeted masters cannot be deleted. There is no arbitrary multi-centre selection, payroll/stock budget by centre or centre-level closing. |
| KL-64 | Foreign vouchers are all-or-nothing | Every line on a foreign voucher is entered in the same foreign currency. There is no per-ledger currency or mixed foreign/base lines, so the cash/bank line included on a foreign voucher also appears in the currency ledger-balance report. |
| KL-65 | Resolved — realised forex settlement matching added 2026-11-21 | Foreign receipt, payment and note lines are matched FIFO against same-currency party invoices. The report shows matched foreign amounts, invoice carrying rate, settlement rate and realised gain/loss, and posts the unposted difference once through Forex Gain or Forex Loss. Posted revaluation moves the carrying rate before later matches so the same gain is not counted twice. |
| KL-66 | Forex revaluation is manually posted | The report posts one Journal per date that adjusts foreign asset/liability ledgers and books the net difference to Forex Gain or Forex Loss; the P&L and balance sheet disclose posted realised and unrealised amounts. It does not automatically reverse a prior revaluation, produce a tax effect, or provide a dedicated revaluation history beyond the voucher list. |
| KL-67 | Foreign inventory and explicit bill allocation are blocked | Foreign vouchers cannot carry stock items or manual bill-wise allocations. Receipts and payments are instead matched FIFO to same-currency party invoices in the Forex report, and the realised difference can be posted from there. |
| KL-68 | Exchange rates are manual | Rates have a date and an INR-per-unit value and can be added, edited, redated or deleted from the rate history; deleting a rate can leave earlier vouchers without a matching rate for revaluation. There is no live feed, inverse/cross-rate, rate spread or rate audit beyond the app log. A voucher uses the latest rate dated on or before its date. |
| KL-69 | No foreign openings or ledger currency | Ledger opening balances are base INR only. Ledgers do not carry a currency, and there is no foreign-currency bank/cash account model. |
| KL-70 | Bill detail covers Sales/Purchase invoices only | The Bill-wise register and Party statement bill table list Sales and Purchase invoices. Same-side journal or adjustment lines remain in the ledger statement and can still look bill-like to the ageing engine; they are not shown as bills in the new detail. |
| KL-71 | Bill timeline added; no timeline-only print layout | The register has a From/To bill period plus a status-as-on date and optional comparison date. Listed bills show settlements during the interval, closed bills, status changes and an expandable dated timeline of raise, settlement and overdue events. The comparison totals settlements across all bills, including bills outside the selected bill period. A bill's timeline can be downloaded as CSV; there is no dedicated timeline-only print layout. |
| KL-25 | Resolved — bill-wise register and party statement added 2026-11-18 | Bill references, due dates, allocations, ageing, a settled/open bill register and a party statement with bill detail are available. Remaining bill limits are KL-31 and KL-70/KL-71. |
| KL-26 | Limited advanced voucher types | Saved recurring templates can prefill a weekly/monthly/quarterly/yearly voucher, or post when due and advance their next date; all due templates can be posted in one action. Posting is user-triggered rather than a background scheduler. There is no post-dated voucher type, memorandum, optional or reversing voucher. The Cheque / DD register is a report over ordinary vouchers. |
| KL-27 | Limited document numbering | Masters → Document numbering can set the next number for each voucher type above the last used number. There are no prefixes, suffixes, multiple series or per-year reset rules. |
| KL-28 | Limited interest and cash forecasting | A simple overdue-interest report and a 30-day cash-flow forecast from open bills exist. Interest can be posted as a Journal with incremental accrual and duplicate protection. A company consolidation report adds company-wise and combined totals without eliminations. There is no compounding, recurring scheduled cash flow, ownership adjustment or statutory consolidation. |
| KL-29 | Limited comparatives | Year comparison exists, and Statistics has summary cards, one monthly sales/purchase trend chart, customer/supplier, stock-position, working-capital and expense-head tables, and a three-month run-rate outlook. There are no multi-period report columns, configurable chart ranges, other chart types, dashboard customisation, seasonality/growth modelling or statistical forecasts. |
| KL-30 | Report presentation is fixed | Every report shares the app's screen and browser print layout, and reports can be downloaded as CSV or Excel. There is no custom print-layout designer, branded PDF or scheduled email delivery. |
| KL-31 | Opening balances are simple | Opening balances are ledger-level Dr/Cr with no bill-wise or cost-centre opening allocation. |

## Banking, cheques and reconciliation

| ID | Limit | Current behaviour / consequence |
| --- | --- | --- |
| KL-32 | Bank statement import is CSV only | CSV, OFX, QIF, MT940 and Excel workbooks are supported. No live bank feed. |
| KL-33 | Auto-match is configurable, still one-to-one | Signed amount within an optional tolerance, a configurable date window and narration-word overlap ranking. It still matches one statement line to one voucher; there is no split or many-to-one matching. |

| KL-36 | Manual instrument status is a flag | A cheque/DD can be marked cleared, stopped or cancelled manually, or restored to the automatic post-dated/due/reconciliation status. These are flags only: they do not post entries, alter the voucher, or notify a bank. |
| KL-37 | Instrument allocation and lifecycle | A voucher can store multiple cheque/DD instruments with bank, number, date and amount; the form adds/removes rows, amounts must reconcile to the bank-line total, the register flattens each instrument and status changes target one instrument. There is no automatic number allocation, split bank posting or full issued-instrument lifecycle history. |
| KL-38 | Cheque print is a browser preview | Only cheque payments can be printed. Alignment depends on the browser and printer; there are no MICR, bank-specific stationery presets, overlay calibration or cheque-number pre-printing. |
| KL-39 | Instrument printing is a browser preview | Cheques, DD payments, receipt instruments and contra vouchers have print previews (cheque, DD advice, deposit slip, contra deposit/withdrawal advice). They are not bank-issued formats or validated receipts, and alignment is printer-dependent. |
| KL-40 | Register scope and cheque-book master | Cheque / DD register covers post-dated, due, cleared, stopped and cancelled instruments and can be filtered by bank, party text or cheque-number range. A cheque-book master stores the bank, prefix, range and next number, blocks overlapping ranges and protects books that contain recorded instruments. It does not print or allocate numbers automatically, and there is no full instrument lifecycle history beyond recent manual status changes. |

## Inventory and manufacturing

| ID | Limit | Current behaviour / consequence |
| --- | --- | --- |
| KL-41 | Inventory is still shallow | Units, stock groups/items, item lines on four voucher types and weighted-average valuation, now with godowns, batches, transfers, orders, stock counts, stock ageing, BOMs and production. Production posts stock/WIP journals; opening stock and manual stock adjustments still need explicit journals. No batch-wise cost layers or partial-completion WIP. |
| KL-42 | Resolved — godowns, batches and batch-level rates added 2026-11-20 | Godowns, transfers, optional batch tracking and expiry dates exist, and stock items carry an optional reorder level with low-stock flags. Dated counts record book and counted quantities by godown and batch, but they do not post adjustments or value differences. Batch valuation uses a per-batch moving average of receipt costs. There is no FIFO/expiry consumption, automatic reordering or job work. Production accepts a wastage quantity that consumes extra components, but there is no separate wastage valuation or scrap stock account. BOM components cannot be batch-tracked. |
| KL-43 | Orders and quotations added; full order cycle missing | Sales/purchase orders carry up to 50 item lines, status and a voucher prefill that tracks fulfilment across multiple linked vouchers. Quotations can be converted to sales orders. Delivery notes and goods receipts copy remaining order quantity but are non-posting documents: they do not move stock or confirm acknowledgement. There are no rejection notes, discounts or additional costs. Item selling and purchase prices feed a price-list report. |
| KL-44 | Stock posting covers production only | Production posts component, labour, overhead and finished-goods entries through Stock in Hand and Work in Progress. Opening stock, purchases/sales and stock adjustments are not automatically journalised, so financial statements remain ledger-driven and the Inventory screen reports the unposted difference. |
| KL-45 | Limited stock reporting | Stock Summary (with reorder-level low-stock flags), godown balances, batch balances, approximate FIFO stock ageing, per-item movements and a stock count register with counted/book differences exist; batch-tracked items are counted per lot and can record stock found in an unlisted lot. A dedicated Reorder watch report shows shortfall and estimated purchase cost, a Price list shows selling/purchase prices, and Stock value analysis breaks closing value down by stock group and godown with totals. Batch balances include a closing-value total. A count's differences can be posted as a SADJ stock adjustment, which changes on-hand quantities and stock value at weighted-average cost but deliberately posts no ledger entry. A batch value by item report sums each item's per-batch moving-average value. |
| KL-46 | Base and one alternate unit per item | A stock item can carry one alternate unit with a six-decimal conversion factor. Voucher item lines can be entered in either unit; quantities convert to base stock, entered quantity/rate are retained for display, and line amounts are preserved for valuation. There are no compound units, multiple alternates or unit-specific pricing. |

A credit or debit note can link to one matching original invoice, and the GSTR-1 credit-note table shows that reference. There is no invoice-wise reconciliation against the original values, CDNR matching, amendment chain or multiple-invoice linkage. |
| KL-80 | GST rates use date windows | A rate can carry effective-from and effective-to dates and is selectable inside that window; rates with the same percentage and cess can coexist under different windows. Posted vouchers keep their saved rate. There is no automatic schedule that creates the next rate or notification when a window ends. |
| KL-81 | TDS/TCS voucher scope | TDS is deducted only on purchase vouchers and TCS collected only on sales vouchers. Journals, credit/debit notes, receipts, payments and advances cannot carry a deduction, and TDS on an advance or a part-payment must be journalled manually. Bill settlements cannot exceed the net party amount after deduction. |
| KL-82 | Per-line sections, one deductee | Each taxable line can carry its own TDS/TCS section or be marked exempt; deductions aggregate by section and the voucher-level section remains a default. There is still one deductee/party per voucher, no multiple deductees, and no higher-rate logic for a missing or invalid PAN. |
| KL-83 | Thresholds are informational | Section thresholds are shown in a financial-year threshold watch but never enforced on a voucher. Aggregate-payment thresholds must be judged by the user, and the watch uses the selected financial year to date. |
| KL-84 | Challans are tracking records; quarterly return working papers exist | Challans are stored separately from vouchers with tax, optional late fee and optional interest, and they do not post entries or reconcile against deductions. Deductee-and-quarter certificate working papers and downloadable 26Q/27Q/27EQ CSV/JSON working papers now exist, but there is no TRACES, generated/signed Form 16/16A or filing history. |
| KL-85 | Resolved — GST and TDS/TCS can share a voucher 2026-11-21 | A GST purchase or sale can also carry TDS/TCS. Tax is calculated on the taxable value, then TDS is deducted from the tax-inclusive party amount or TCS is added to it; the voucher stays balanced and backup-compatible. |
| KL-86 | TDS/TCS needs one balancing line | A TDS/TCS voucher must have exactly one party, cash or bank line on the balancing side; split payments must be merged. TDS/TCS is not available on foreign-currency vouchers. |
| KL-87 | Single TAN; section windows and history added | One TAN per company, no deductor PAN or multiple registrations. A section can carry effective-from/effective-to dates; editing its description, rate, threshold or window records up to 25 earlier values, while its kind and code stay fixed. Posted deductions keep their snapshot. There is no automatic rate-change schedule or statutory section-history feed. |
| KL-88 | Local section template | Seeded sections, rates and thresholds are a convenience template, not verified statutory rates. Surcharge, health-and-education cess and section-specific exemptions are not calculated. |
| KL-89 | Fixed monthly payroll with manual paid days | Each employee carries fixed monthly amounts per pay head. Joining and exit months, plus a paid-days entry per run, prorate amounts by calendar days. A leave register tracks opening, used and remaining casual/sick/earned balances, but it does not automatically change paid days. Attendance CSV can preload paid days by employee name or code for review, and a template button fills employee names. A pay head can also be a percentage of fixed Basic, so bonus or allowance heads recalculate with Basic and proration. Bonus, arrears and corrections can be posted as an adjustment run with explicit signed employee/pay-head lines. There is no overtime, gratuity or general formula language. |
| KL-90 | PF/ESI/PT use a simple calculator; working papers export | PF, ESI and professional tax are deduction pay heads with a reporting tag. A calculator applies configurable employee and optional employer PF/ESI rates, wage ceilings, Basic as the PF wage, gross as the ESI wage and a fixed PT amount. A payroll run posts the employer PF/ESI share to the payable ledgers. Monthly EPF ECR and ESI CSV/JSON working papers use UAN/ESIC numbers and stored run snapshots; quarterly 24Q and annual employee Form 16 papers use payroll gross and TDS. They are local papers, not portal uploads or acknowledgements. State PT slabs, ECR upload validation and a signed Form 16 remain absent. |
| KL-91 | Resolved — supplementary and adjustment payroll runs added 2026-11-21 | A month has one regular run plus any supplementary runs for uncovered employees and adjustment runs with explicit signed employee/pay-head deltas. Each run posts its own Journal; reversal marks the run, blocks a second reversal, removes both vouchers on delete and excludes the run from summaries. Run kinds, reasons, paid-day snapshots and restored totals survive backup round trips. There is still no bulky upload format, bank validation, payment matching or payslip email/PDF. |
| KL-92 | Flat employee master | Employees are a single list with optional code, designation, PAN, UAN, ESIC number, joining/exit dates, bank name, account number and IFSC. Pay-structure changes append a salary revision with the full snapshot and an optional revision date, but there are no future-effective revisions or automated increment schedules. Departments, designations and locations masters, advances, loans, reimbursements, multi-currency pay and CTC history remain absent. |
| KL-93 | Pay heads support fixed amounts or a percent of Basic | A pay head has a posting ledger, an optional PF/ESI/PT/TDS tag and either a fixed monthly amount per employee or a percentage of fixed Basic. Percentage heads recalculate in runs, payslips and proration. There is no general formula language, effective-date history, pay-head groups, rounding rules or statutory rate tables. |
| KL-94 | E-invoice JSON is a draft only | The download follows NIC field names but is not validated by a schema, signed, registered with an IRP or acknowledged. There is no IRN, QR code, cancellation, amendment, consolidated B2B reporting, credit/debit-note e-invoice or IRP error handling. The aggregate-turnover applicability test is not applied, so every B2B invoice is listed for review. |
| KL-95 | E-way bills are working drafts with validity | Part B transporter name, transporter ID, vehicle number and distance can be saved per invoice and appear in the draft JSON. Distance-based validity is calculated at one day per 200 km or part and shown with its expiry date. There is no portal submission, extension, cancellation, consolidated e-way bill or multi-vehicle movement. The threshold is a configurable working value, not a state/goods rule engine. |
| KL-96 | GST contact data is optional | Trade name, registered address, city, PIN, phone and email, plus party address/city/PIN/phone/email, are optional free-text fields and flow into draft e-invoice seller/buyer details. Missing address fields block e-invoice readiness but are not enforced on vouchers; there is no ship-to/bill-to, export/SEZ or address master. |
| KL-97 | Tax-audit reports are informational | Turnover, GST/ITC and TDS/TCS reconciliations plus the ten-clause checklist are working papers, not a Form 3CD, audit opinion, 44AB applicability decision or disclosure set. The ₹1 crore/₹10 crore thresholds are flags only. A digital-receipt percentage and 95% test flag are calculated from bank versus cash receipts, but applicability still needs professional review. |
| KL-98 | E-invoice lines are invoice-rate only | Voucher ledger lines can carry their own GST rate and the return working papers split mixed-rate invoices, but the e-invoice draft still uses the voucher-level rate for every item. There is no per-item discount, shipping/other charge, pre-tax value, cess non-advalorem, state cess or service SAC master. Unit mapping is limited to common symbols and falls back to OTH. |
| KL-99 | Compliance tasks remain local; GST late fee can be estimated | A user-managed compliance calendar stores task titles, categories, due dates, notes, done/open status, an optional filed-on date, acknowledgement reference, late fee and interest. A GST late-fee/interest calculator supports due dates, nil returns and the GSTR-9 turnover cap, but task amounts remain manually entered. There is no GST/TDS/e-way filing or automatic acknowledgement fetch, and statutory registers remain absent. |
| KL-100 | Stock transfers can be edited; deletion is dependency-checked | A transfer can be reopened, its date/godowns/items changed and saved under the same number, with every line revalidated against source stock. Deleting a transfer is refused when later destination-godown activity would become negative without it, including batch balances. There is no reversal document or inter-branch accounting entry. |
| KL-101 | Batch cost uses a per-batch moving average | Purchases add their receipt rate to the batch and issues consume that batch's average, falling back to item weighted-average cost before any receipt. There is no FIFO/expiry picking or automatic batch selection on sales; a 90-day expiring-batch report is available in Inventory. |
| KL-102 | Orders track quantities but do not reserve stock | Orders carry up to 50 item lines and record fulfilled quantities across linked vouchers. Open sales orders show committed and available-to-sell stock in the Stock Summary and Reorder watch; this is a commitment view, not a hard allocation. An order can be short-closed with the unfulfilled remainder explicitly written off and a reason; reopening restores it. Closing or cancelling records an optional reason, and overdue delivery dates are flagged. Delivery notes/goods receipts copy remaining quantities. A linked order cannot be deleted. |
| KL-103 | Multi-level BOMs explode sub-assemblies | A BOM has one finished item and up to twenty direct components. If a component has its own BOM, production recursively explodes it into raw components with cycle detection; the sub-assembly is a phantom and is not stocked separately. Wastage and optional labour/overhead exist. There are no alternative components, by-products, scrap/rework, job work or separate sub-assembly stock postings. |
| KL-105 | BOM components cannot be batch-tracked | A batch-tracked stock item cannot be used as a BOM component, so raw materials must be untracked. Finished output may be batch-tracked. Multi-level BOMs can use non-batch sub-assemblies, but BOMs remain fixed recipes with no revisions or effective dates. |
| KL-106 | Production cost is component cost plus entered conversion | Output enters stock at the consumed components' weighted-average cost plus optional labour and overhead, and a balanced production journal is posted through Stock in Hand and Work in Progress. Machine and power costs must be entered as overhead; there is no variance account or partial-completion WIP. |
| KL-107 | Production is single-godown; deletion is stock-checked | All components must come from one godown and all output goes to one godown. Delete is refused when removing the output would make its stock negative on or after the production date, including a later batch-specific balance. There is no reversal, edit or approval workflow. |
| KL-108 | Conservative merge only | Recent base revisions are merged by record id when independent company, ledger or voucher changes can be proven disjoint, including work by company-scoped accounts while hidden companies are preserved. Same-field edits and voucher-line changes conflict rather than merge; concurrent vouchers with the same type/number are automatically renumbered. Voucher edit leases are hashed, expire automatically and are enforced on server saves, but they cover vouchers only and are not database transaction locks. Only the last 20 revisions are retained; accepted merges record a hash-chained field-path summary, but not the changed values, and a stale save outside the retained window must reload. Reload snapshots the local copy before replacing it. |
| KL-109 | Tally XML import is accounting plus stock | Account groups, ledgers, stock groups, stock items with opening quantity/rate, balanced accounting vouchers and matching voucher stock lines import. Custom account groups need an existing standard parent; custom top-level groups and units must already exist. Account-group nesting is preserved parent-first. Stock groups are imported flat, so their Tally parent hierarchy is ignored. Tally batch masters import as opening batches with quantity and expiry on batch-tracked items, and voucher batch allocations import as names/expiry on lines. Opening batches sit in the primary godown; a batch master's godown is ignored. Bill allocations, cost centres, GST/TDS detail and original voucher numbers do not import. Imported vouchers are renumbered. Tally APIs and webhooks are absent. |
| KL-110 | Tally XML parser is a subset | The parser handles common All Masters and voucher exports with regexes, not a full namespace-aware XML parser. Unusual Tally templates, multi-currency vouchers, inventory layouts and XML exports with nested optional blocks may be rejected or lose fields. Stock lines that cannot be mapped are skipped while the accounting voucher imports (KL-112). |
| KL-111 | Excel import is one reviewed worksheet | Only `.xlsx` (Office Open XML) is read, not legacy `.xls`, `.ods`, CSV-as-Excel or password/ZIP64 workbooks. One sheet per import: `Ledgers`/`Vouchers` when present, otherwise the first worksheet; there is no multi-sheet merge. It reads cached cell values and does not recalculate formulas. Merged cells, hidden-sheet intent, tables, autofilters and macros are ignored. Dates must be date-styled cells or YYYY-MM-DD text; un-styled serial numbers stay numeric. The converted rows land in the normal CSV review box and obey the same all-or-nothing import rules. |
| KL-112 | Tally stock lines are best-effort | The accounting voucher imports even when its stock lines are skipped. Stock lines are skipped when the item/godown is missing, a batch is missing on a locally batch-tracked item, stock is insufficient, or the item total differs from the voucher because of GST/discount splits. The skipped count and first reason are reported. Stock is not rolled back with the voucher, and batch-wise costing, batch-master godowns and item-level GST/discount allocation are not modelled. |
| KL-104 | Godown quantity is not a valuation layer | Godown balances use the item average cost; transfers do not create a separate godown valuation. Closing stock value is still one company-wide item value. |

The app is now a usable local/LAN accounting system, but the limits below are
still material for production use. They are grouped here because fixing them is
either a larger product change or depends on an external service. “Free” below
means no licence fee: open-source software, the operating system, or a
service's free allowance. Free tiers and allowances change, so verify the
current terms before relying on one.

| RL-01 | Partially resolved — direct R2 backup upload and encrypted JSON downloads added 2026-11-19/20 (KL-04, KL-13) | Verified SQLite snapshots can now be uploaded to R2 with a scoped bucket token; the local copy is kept if the upload fails. Downloaded JSON backups can be passphrase-encrypted in the browser, and setting `ZL_BACKUP_PASSPHRASE` encrypts new server/R2 backup files (including automatic uploads); without it those snapshots remain plaintext. | Enable the R2 variables and a lifecycle rule, then test a download/restore. ### Recommended order

1. **Do first, low effort:** OS disk encryption; R2 offsite copies of the existing verified snapshots (optionally restic-encrypted); Caddy/mkcert TLS.
2. **Do next, contained product work:** the read-only API/OpenAPI with hashed tokens is complete. Next contained work is a write API/webhook design only if a concrete integration needs it.
3. **Plan as larger projects:** encrypted application storage/SQLCipher; incremental master normalization; write API/webhooks; statutory portal integrations.

A free solution is not automatically a production solution. The remaining work
still needs an owner, a restore drill, a key-recovery plan, and a decision about
whether the app may use the internet at all.

## How to use this register

1. Pick a limit by ID when planning the next stage; do not silently widen scope.
2. Add a new row when a new deliberate limitation is introduced.
3. When resolved, change the row to **Resolved** with the date and release/commit
   reference, and update `ROADMAP.md` and `README.md`.
4. Keep this file focused on known gaps, not wishes that have no product decision.
