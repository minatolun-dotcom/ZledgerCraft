# Cloud integration plan

Last updated: 2026-11-19

This is the working record for the Cloudflare Pages, Cloudflare R2, Resend and
Neon integration. It records the agreed phases, decisions, implementation
status and verification evidence. Update the progress log after every phase.

## Current architecture and constraints

- The browser app remains a dependency-free static bundle. `dist/ZledgerCraft.html`
  is generated by `node build.mjs`.
- The optional server is Node-based: `serve.mjs` uses `node:http`,
  `node:sqlite`, local files and timers. It runs as a Neon Function (Node 24);
  `neon-function.mjs` adapts Web Requests and `serve.mjs` skips its listener in
  function mode. It is not a Cloudflare Workers runtime port because Workers
  lack `node:sqlite`.
- `server-workspace.js` and `server-auth.js` use synchronous SQLite APIs for the
  local/LAN mode. Neon mode uses the asynchronous `server-pg.js` workspace store
  and Neon Managed Auth through `server-neon-auth.js`; the synchronous SQLite
  path remains the fallback.
- The browser app still has no server framework or bundler. Neon Auth calls are
  proxied by `serve.mjs` behind same-origin `/api/auth/*` routes, so the static
  bundle does not need the Neon SDK.
- Cloudflare Pages hosts the static app. A Cloudflare Worker proxies
  `/api/*` on the custom domain to the Neon Function, keeping cookies
  same-origin without exposing the function hostname in the browser.
- R2 is object storage, not a database or scheduler. Resend is email delivery,
  not a scheduler. Neon is a database, not an API host by itself.

### Phase 4 — Approvals and access controls

Status: **in progress (4A and 4B complete 2026-11-19)**

- [x] **4A. Per-account MFA policy (SQLite/LAN).** Accounts can be marked
  `require_mfa` after TOTP enrollment. Sign-in refuses an account that requires
  MFA without an enrolled secret, and owners must clear the requirement before
  disabling 2FA. Recovery codes clear both MFA and the requirement to avoid a
  lockout. This is enforced by the SQLite `AuthStore` and exposed in the owner
  account panel; the policy is unavailable in Neon Managed Auth mode, which has
  no TOTP support. The route returns `501` there.
- [x] **4B. Voucher approval workflow.** A company can require owner approval
  for staff vouchers. Pending submissions are stored separately from posted
  vouchers, so they never affect ledgers, reports or inventory until approved.
  Owners approve (assigning the real voucher number) or reject with a note;
  proposers cannot decide their own voucher. The server rejects accountant
  attempts to add posted vouchers or alter existing submissions while the
  policy is on. The voucher screen shows the approval queue and status.
- [ ] **4C. Read-only API and OpenAPI contract.** Hashed bearer tokens, scopes,
  versioned read endpoints and rate limits.

## Security decisions

- R2 credentials must be scoped to one bucket and stored as server secrets.
- Backups are sensitive. R2 provides encryption at rest, but provider-side
  encryption is not a substitute for client-side encryption or an offline key.
  Do not put the only copy in the same account as the live database.
- Password-reset tokens are stored only as hashes, expire quickly, are single
  use and never reveal whether an account exists.
- Email addresses are optional; existing username-only accounts must continue to
  work.
- Resend failures must not block a successful local backup. Report the failure
  and keep the local verified snapshot.
- Never log reset tokens, Resend keys or R2 secrets.
- Neon Auth owns password hashes and reset tokens. The app never stores Neon
  passwords; it maps the Neon user id to the existing role/company-scope profile
  and issues its own HttpOnly app session. Neon mode has no TOTP/MFA; keep the
  SQLite/LAN mode if MFA is required until a second factor is rebuilt.
- `.env.local` is git-ignored and loaded at server start. A secret pasted into
  chat should be rotated, not copied into the project.

### 2026-11-19 — Phase 2 limit fixes: shared limits and durable backup recovery

- Moved the short source-rate limits out of process memory. `AuthStore` and
  `PostgresAuthStore` now accept window/max/lock options on the existing
  `auth_login_limits` table; login uses an eight-failure/minute source bucket
  and reset requests use a five-request/15-minute bucket. Every function
  instance reads and writes the same Postgres row, and SQLite/LAN mode uses the
  same interface. The Worker now forwards the real client address in
  `x-zl-client-ip`/`cf-connecting-ip`; production testing found that relying on
  `x-forwarded-for` alone keyed limits to rotating Cloudflare egress addresses.
- Added R2 `ListObjectsV2`, signed `GET`/`DELETE` helpers, and remote listing,
  download and restore in the owner backup screen. If a function instance has
  lost its `/tmp` backup, the list still shows the R2 object and restore
  downloads and verifies it before the normal pre-restore backup.
- R2 remains the durable destination; retention is still delegated to a bucket
  lifecycle rule. Neon Auth still has no MFA and Neon Functions can cold-start.

### 2026-11-19 — Phase 3: scheduled reports and operational alerts

- Added `server-reports.js`: HMAC-signed expiring links, a read-only daily
  management summary and HTML/text email rendering. The summary uses live
  trial-balance and ledger totals; it is not a workspace dump.
- Added `zl_report_settings` (Postgres) and `report_settings` (SQLite) plus the
  owner endpoints `GET/PUT /api/reports/settings`, `POST /api/reports/preview`
  and `POST /api/reports/send`.
- Added the public signed report route at `/api/reports/daily`; no session is
  required, but the token must be valid and unexpired.
- Added `/api/internal/scheduler`, guarded by the Neon trigger invocation
  header or a `ZL_SCHEDULER_SECRET` Bearer token. It runs the daily backup check
  and sends the report once per UTC day when enabled.
- Declared the `daily-operations` Neon Function Trigger at `30 2 * * *`; local
  servers use an hourly timer with the same due logic. No Cloudflare Worker
  cron builds a report.
- Added owner controls in Companies → Server accounts for recipients, enabled,
  send-now and signed-link preview.
- Persisted each report attempt's time and error (`last_attempt_at`,
  `last_error`) and surfaced the latest failure in the owner panel. Existing
  SQLite/Postgres tables are migrated in place.
- A failed scheduled report now alerts `ZL_ALERT_EMAIL` through Resend once per
  UTC day; manual sends remain visible in the owner panel without paging.
- Added `server-pdf.js`, a dependency-free A4 PDF writer for the branded daily
  summary, and attached the PDF to report emails through Resend.
- Added `report_attempts`/`zl_report_attempts` with the latest 50 attempts and
  exposed the ten newest, including source, recipients, status and error, in the
  owner report panel.
- Added matching backup-attempt history (`backup_attempts`/`zl_backup_attempts`)
  for daily, manual, warning and failed backups, with the ten newest in the
  owner backup panel.
- Started Phase 4 with the SQLite/LAN `require_mfa` policy: owners can require
  enrolled TOTP for an account, disable is blocked while required, and recovery
  clears both MFA and the requirement. Neon Managed Auth remains unable to
  enforce TOTP, so the route returns 501 there.
- Added Phase 4B voucher approvals: a per-company owner-approval policy, a
  separate pending queue, approve/reject/remove actions, proposer/approver
  attribution, self-approval blocking and server-side prevention of accountant
  direct posting. Pending vouchers never enter the posted books.
- Remaining 4B limits: pending submissions cannot be edited in place, there is
  no multi-level approval matrix, and concurrent pending-queue merges rely on
  the normal workspace conflict flow rather than a dedicated merge.
